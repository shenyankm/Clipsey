# URL 读取策略实验

日期：2026-10-11；生产实现基线：`7b1d921`。本记录对应原型实验阶段，当时未修改生产存储代码或数据库版本。后续[生产候选与验收](./performance-indexed-url-cache.md)已验证迁移和失效，也记录了批量写入退化。整个性能优化目标仍在进行，延续[日期与后台观测](./performance-normalization.md)。

当前后续实现及测量见[批量写入与单库 URL 索引验收](./performance-write-index.md)。

## 比较范围

比较四种策略：当前全库缓存；扫描原始 URL 索引键、仅访问命中记录的 `IDBRecord.value`；按规范化基础 URL/创建时间/ID 建复合索引；复合索引配合独立页缓存。后两种在临时实验数据库中实现，保留当前八个索引，再新增一个派生字段和复合索引；不涉及用户数据库。

Chromium 的 `IDBRecord.value` 访问器调用反序列化函数，键访问器独立处理索引键，见 [Chromium 实现](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/renderer/modules/indexeddb/idb_record.cc)。这是键扫描候选的依据，不证明扫描全库的整体成本足够低。

macOS、Node.js 22.23.2、Headless Chrome 155.0.0.0，独立临时目录，真实 IndexedDB。分别测 100 和 10,000 条完整日期记录，正文约 650 字符并带 HTML。稀疏组每 1,000 条命中一个基础 URL；密集组全部属于该基础 URL，高亮去重后返回一半记录。

来源包含大小写主机、默认端口、尾斜杠、片段、查询参数不同或顺序不同的变体；创建时间有重复值。每次计时外逐字段比较结果，验证顺序、精确查询优先及高亮去重；页缓存另外验证切换同一基础 URL 的查询参数后仍正确。

每项预热一次，再七次取中位数；两轮交换四种方法的运行顺序，串行运行，不同时测试或构建。冷指清空应用内存缓存，数据库已经建好，不是磁盘冷启动或后台休眠后的启动。两个无缓存候选每次都查询数据库，`warm` 标签只表示重复实验分组。缓存热读每样本循环至多 1,000 次，限制累计返回对象数约为 20,000，避免为计时制造过多大数组。

## 主要结果

| 10,000 条，ms | 当前全库缓存：第一轮 / 第二轮 | 复合索引与页缓存原型：第一轮 / 第二轮 |
| --- | --- | --- |
| 稀疏冷读取，返回 10 条 | 91.2 / 93.8 | 0.3 / 0.3 |
| 稀疏热读取 | 0.0024 / 0.0024 | 0.0024 / 0.0026 |
| 密集冷读取，去重后返回 5,000 条 | 83.9 / 85.3 | 81.6 / 102.6 |
| 密集热读取 | 0.475 / 0.425 | 0.400 / 0.425 |

稀疏组的候选同时避免加载无关记录，并保留重复读取的缓存收益。密集组冷读第二轮增加约 17ms，尚不能证明该策略适合直接替换生产路径；不能只引用稀疏组的巨大差值宣称项目整体改善。

100 条稀疏冷读取，当前为 0.6 / 0.7ms，页缓存原型为 0.1 / 0.1ms；密集冷读取为 0.7 / 0.6ms，对照 0.6 / 0.7ms。热读取大致相当，受时钟粒度和主机波动影响，不推算稳定体验收益。

单纯键扫描的 1 万条稀疏冷读取为 86.5 / 88.4ms，重复读取为 80.1 / 85.1ms；密集冷读为 100.0 / 106.7ms。它仍读取全库的底层数据，且缺少热缓存，未采用。

没有页缓存的复合索引在稀疏组读取约 0.2–0.3ms，但密集组重复查询约 81–100ms。只替换数据库查询、放弃缓存，会明显损害大量命中时的重复读取。

## 分配量采样

另行运行两轮 `HeapProfiler.startSampling/stopSampling`，平均间隔 16,384 bytes，包含被大小 GC 回收的对象，调用树 `selfSize` 求和，七次取中位数。每次操作前清空相应缓存并强制 GC；切换数据组时重新建立两套数据库，其余操作均为只读。准备不在采样内，完整结果校验在停止采样之后，操作只保留结果，不把整数组经 CDP 返回。

| 10,000 条冷读取，十进制 MB | 第一轮 | 第二轮 |
| --- | --- | --- |
| 稀疏，当前全库缓存 | 22.51 | 22.09 |
| 稀疏，键扫描 | 1.86 | 1.98 |
| 稀疏，复合索引与页缓存 | 0.050 | 0.017 |
| 密集，当前全库缓存 | 20.45 | 20.61 |
| 密集，复合索引与页缓存 | 20.87 | 21.31 |

这是操作期间 V8 分配量的近似估计，不是峰值存活堆、C++ 底层缓冲、进程 RSS 或磁盘占用。小分配接近采样间隔，不能据此给出精确百分比；100 条中的零样本不表示没有分配。采样器开启期间的时间没有用于耗时结论。

原始样本及环境：[performance-url-read-results.json](./performance-url-read-results.json)。一次反序运行因实验页查询参数路由遗漏而超时，修复后完成；一组错误复用最后数据集的分配样本已剔除，修复后每项在采样结束后验证完整结果。

## 正式接入所需验证

原型页缓存只服务一个基础 URL，不能替代全库缓存。后续需要完成生产实现，并验证：

- 派生索引的旧数据回填、事务回滚及数据保留，包括不符合当前日期/ID 假设的旧记录；不能把异常迁移成数据缺失。
- 保存、添加、删除、整体导入和迁移等写入路径同步维护索引；导出与其它读取不暴露派生字段。
- 有界页缓存与全量读取共存，跨 URL 并发、同基础 URL 不同参数、写入失效、旧快照重试、失败传播及返回对象隔离。
- 密集与中等命中比例的读取成本、新增索引的写入与迁移成本，以及实际扩展高亮、备份和同步行为。

本轮没有重新运行生产单测、构建和界面验收，因为生产代码未修改；上述原生矩阵及结果断言已执行。精确峰值、Edge/Firefox 运行时、低端硬件和真实用户分布仍未验收。

```sh
node scripts/performance.mjs --url-read
node scripts/performance.mjs --url-read --reverse
node scripts/performance.mjs --url-read --allocations
node scripts/performance.mjs --url-read --allocations --reverse
```

不使用 `--baseline`，每次运行在同一页面比较当前算法与候选；`CHROME_PATH` 可替代 Chrome 路径。键扫描需要实验浏览器支持 `getAllRecords`，没有因此改变生产浏览器兼容性。
