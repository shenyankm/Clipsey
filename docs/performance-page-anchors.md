# 未访问深页的有界游标边界验收

2026-10-12；基线 `5136257`，承接[深页复访缓存](./performance-page-keys.md)及[未采用的一次主键扫描实验](./performance-one-pass.md)。以 10,000 条为主、100 条为辅，另检验 20,000 条重复索引值。完整样本、源码/构建 SHA-256、原型和界面结果见[原始数据](./performance-page-anchors-results.json)。

## 结果与实现

Chrome 155 两轮中，创建时间排序的相邻新深页 21.8–23.2ms → 0.7–0.9ms，跨 25 页的新页 23.2–24.6ms → 1.8–2.3ms。20,000 条对照和长正文重复键慢方向见下表；收益依赖位置、键分布与浏览器，没有消除所有定位成本。

沿用每连接最多 16 页、256 KiB 字段权重的主键缓存，每页多存最多两个原生游标边界：逻辑位置、索引键与主键。新页只考虑相同索引、方向且当前版本一致的边界，选择推进距离比原 offset 更短、且反向重复组扫描上界也更短的一端。例：已访问页的末位置是 319，新页起点 320，只推进一条；前一页用反方向到达其末位置，再反转本页主键，保持请求排序。

重复索引值使用索引键与主键联合定位，避免把同组的第一条当成目标。只有起始游标与边界不同时调用 [continuePrimaryKey](https://www.w3.org/TR/IndexedDB/#dom-idbcursor-continueprimarykey)，相同位置不再推进。距离为零不调用 advance，部分末页按当前精确 total 截断反向读取。

索引键从真实游标读取，不从正文字段推算。按正文排序时，两端索引键就是正文字符串，也计入字段预算；不缓存 HTML 或返回对象。结果仍在同一 clips/metadata 只读事务内读版本与精确总数，并用本页主键执行新鲜 get。写入、删除、清空、缺标记或换连接后不使用旧边界，完成前、失败或 abort 时不发布新边界。

最多仍是 1,600 个缓存主键，另加最多 32 个边界。主键沿用每页 128 字节、每键 32 字节加 UTF-16 长度的估算；边界增加每个 64 字节、主键 UTF-16 长度和索引键字段长度，字符串数组另计成员开销。合并权重超过预算时先去掉边界，保留原来可缓存的主键；再按原有 16 页/256 KiB 规则淘汰。字段权重不是实际堆、峰值或 RSS 上限。

边界限字符串主键，索引键限字符串或字符串数组。数字、Date 或其他索引键仍能复用原主键页缓存，新页保留原游标；范围、unique、浅页、特殊 offset/页量、其他表及没有合适边界的页不采用新定位路径。范围等不可缓存页不采集边界，避免无用的临时键对象。没有新依赖、schema、权限或公开 API。

## 较早页面与重复键的反向成本

另从第 16、100 页首次访问前一页，覆盖五来源和两方向。反向范围游标从整个重复键组末尾开始，不能只比较 advance 的距离。生产选择现在用同版本的后续不同索引键约束组末位置；没有该边界时采用 total − 1 的上界。仅当反向扫描上界比原 offset 更小时采用，主表键唯一不需要该约束。同方向仍使用原生联合定位。

没有成本约束的原型保留用于揭示取舍，不等同于生产实现。修复前诊断中，5,000 条相同正文索引值使升序第 16 → 15 页约 32ms；第 100 → 99 页约 23ms。生产现在在这些不确定边界下回退原路径。某些降序重复键在 Chrome 的联合定位原本约 1ms，也会保守回退；这避免依赖浏览器对重复组某一方向的偶然快路径，不能宣称选择总是最快。

## 测量过程与复跑

先用独立边界缓存原型检查方向，保留初始 Chrome 正序数据和夹具快照。首轮完整生产矩阵发现范围等无需采集边界，去掉临时分配后重新冻结源码、夹具及脚本，再完整跑最终 16 轮。首轮 16 轮及旧查询源码也单独保留。随后增加早页诊断，发现重复键反向扫描回退；加入成本上界后再次冻结并重跑最终 16 轮。前两组 16 轮和早页诊断均保留，没有混入最终表格。

最终每种夹具/浏览器依次串行运行基线正序、候选正序、候选反序、基线反序；没有测试、构建或 CPU/分配采样重叠。新页夹具的独立原型仍作为另一比较方法交替运行，正式表格只引用生产方法；每次准备及关闭连接都在计时外。原计数夹具检验冷/热、越界、插入/删除，所有时间均包含总数、顺序及完整字段断言。完成全部测量后才运行最终测试、类型、构建和界面检查。
