# Firefox 备份消息传输优化

2026-10-12；基线 `109f792`。继续以 10,000 条为主、100 条为辅。[上一轮 Firefox 验收](./performance-firefox.md)发现，全量对象消息占备份耗时的大部分。本阶段只优化 Firefox 备份路径。

## 最终改动

Firefox 构建注册 `EXPORT_BACKUP_JSON`：沿用 `exportAllData()`，在后台使用单参数 `JSON.stringify`，通过同一响应封装返回紧凑 JSON。管理页直接把字符串放入 Blob，避免把 10,000 个记录对象逐个传到页面后再编码。Chrome/Edge 保留原有 `EXPORT_DATA` 对象消息路径；编译产物中没有新消息类型。

浏览器判断使用 [WXT 的构建环境变量](https://wxt.dev/guide/essentials/config/environment-variables.html)。没有新增浏览器权限、依赖、数据库版本或持久缓存。原 `EXPORT_DATA`、导出服务、存储/缓存实现、字段过滤、时间/ID 顺序、版本、错误日志范围、下载和确认恢复流程保留。新接口没有 payload，也不暴露缓存引用。

补充后端读取/编码错误的失败响应测试，保证不返回部分备份；下载测试分别验证 Chrome、Edge 对象响应和 Firefox 字符串响应，并保留运行时不可用及恢复错误的覆盖。

## 生产构建的实测

测试用 Firefox 153.0 Nightly，build ID `20260722112722`，geckodriver 0.37.1，macOS arm64。浏览器来自 Playwright 下载，包含测试补丁，不代表正式发行版。使用独立临时配置、真实扩展消息和 IndexedDB，夹具同上一报告：正文约 640 字符并含中文/emoji、HTML、完整日期，45 条同来源，其余不同来源。

同一最终构建比较三种方法：旧缩进对象响应、上轮紧凑对象响应、新后台紧凑字符串响应。每项预热一次、各七次，循环轮换执行位置；第二轮反转规模及方法顺序。逐条数据验证和 Blob 解析在计时外。正式样本与原型分开保存。

计时从页面发消息开始，到 Blob 创建完成。包括后台导出、编码及消息传输，不包括下载写盘、界面渲染或恢复。Firefox 时钟呈整数毫秒精度；没有强制 GC 或采样 Firefox 内存。结果如下，单位 ms，均为七次中位数：

| 场景 | 第一轮 | 第二轮 |
| --- | --- | --- |
| 100 条，上轮紧凑对象 → 新字符串 | 3 → 2 | 3 → 1 |
| 10,000 条，上轮紧凑对象 → 新字符串 | 272 → 124 | 281 → 125 |
| 10,000 条，旧缩进对象 | 274 | 274 |
| 10,000 条，上轮消息往返 | 252 | 259 |
| 10,000 条，新消息往返，包含后台 JSON 编码 | 113 | 119 |

主要规模的整段耗时减少约 148–156ms，约 54–56%。新方法页面的编码时间为 `0ms`，因为编码移入后台，已经计入消息往返；不能据此宣称编码没有成本。100 条的差异接近计时粒度，不宣称稳定的小数据体验提升。

两种紧凑路径的文件字节数完全相同：100 条为 154,457，10,000 条为 15,520,607。逐样本核对所有字段、顺序、Unicode、HTML、日期、备份头及私有字段未泄漏。JSON 格式和内容规则没有再改变。

## 未采用的方案

在临时源码副本中另外比较了管理页直接调用原导出服务。其热缓存耗时更低：Firefox 10,000 条约 25ms，Chrome 约 33.5–34.2ms；但它在管理页建立第二份全量缓存及 URL 索引。Chrome 对象与字符串路径预热后，清空 Blob 并强制 GC，页面的 `usedSize` 约 45.4/45.2MB；直接导出预热后约 74.4/74.3MB，多保留约 29.0/29.1MB。该单次占用差不是峰值、进程 RSS 或泄漏结论，仍足以反对为一次下载长期保留第二份全库缓存，因此没有采用。

同一 Unicode 夹具的 Chrome 原型中，紧凑对象 → 后台紧凑字符串的总耗时为 113.4 → 111.8ms、115.7 → 113.7ms，收益很小。此前 ASCII 夹具的后台缩进字符串方案略慢且总分配增加，见[备份报告](./performance-backup.md)。夹具和编码不同，不能混为同一次实验；也没有证明 Chrome 上稳定且足够大的收益，所以本次只在 Firefox 使用新接口。

Firefox 原型首轮在样本保存之后的旧日志汇总代码抛错；数据核对及原始样本已保存，错误和清理路径保留。它不计作正式通过的验收。最终构建的上述两轮正常退出，支持正式结论。

## 验证与复跑

- 28 个文件、225 个测试通过；类型检查及 Chrome/Edge/Firefox 构建通过。
- 最终 Firefox 两轮各 12 项真实流程通过：两种规模的导入、分页、全量字段隔离、搜索/第二页、标题排序，实际 10,000 条紧凑下载、旧/新格式确认恢复及无效导入保护。每轮三种测量方法的所有样本亦逐条校验。
- Firefox 扩展 URL 来源的非警告脚本错误为空；测试浏览器自身的沙箱/Juggler/附件服务提示保留在驱动日志中。
- 编译产物检查确认，新消息仅存在于 Firefox，Chrome/Edge 不包含它；存储、缓存、数据库及原导出 API 源码哈希与基线相同。
- 实际 Chrome 的既有 17 项管理/备份/搜索/同步/错误流程通过；另验证 10,000 条实际紧凑下载及旧/新格式确认恢复，3 项均通过，页面无异常。

复跑使用更新后的脚本，需先构建 Firefox：

```sh
node_modules/.bin/wxt build -b firefox
FIREFOX_PATH='/path/to/firefox' GECKODRIVER_PATH='/path/to/geckodriver' node scripts/firefox-performance.mjs
FIREFOX_PATH='/path/to/firefox' GECKODRIVER_PATH='/path/to/geckodriver' node scripts/firefox-performance.mjs --reverse
```

脚本同时保留前两种编码的比较，并额外测量生产后台 JSON 路径。下载、输入备份、结果及驱动日志保留在临时产物目录；结束时删除浏览器测试配置。所有正式样本、原型、源码/构建哈希与检查范围见 [performance-firefox-backup-results.json](./performance-firefox-backup-results.json)。

尚未验证正式发行版 Firefox、Firefox 精确峰值/长期内存、冷启动备份、休眠或跨上下文写入期间的备份竞态、低端硬件、真实用户分布及远端 CI。Edge 本轮只有构建、路径与单元检查。既有大 chunk 和 Firefox 商店配置警告保留。整个性能目标仍在进行。
