# 备份生成与消息传输优化

日期：2026-10-12；基线 `1aeb06f`。主要规模为 10,000 条，兼顾 100 条。延续[后台休眠验收](./performance-worker-idle.md)，检查全量响应的实际消费路径。

## 最终改动

生产代码只改一行：备份页面使用 `JSON.stringify(response.data)`，省去缩进和额外参数。文件改为紧凑 JSON，记录、字段、顺序、备份版本、错误日志范围及确认恢复流程保留。`EXPORT_DATA` 仍返回对象，缓存仍复制返回值以隔离调用方，没有新增消息类型、数据库版本、权限或依赖。

现有下载测试补充中文、emoji、引号、换行和富文本，验证数据往返。README 说明新文件格式及旧缩进格式的恢复兼容性。

## 实际 Chrome 测量

Chrome for Testing 153.0.8010.12、独立临时用户目录、构建后的扩展及真实 IndexedDB/扩展消息。正文约 640 字符，带同量富文本，各条来源不同。通过同一 `EXPORT_DATA` 分别执行旧缩进编码、单参数紧凑编码，再创建相同类型的 Blob。

每种规模预热两种编码，各测七次取中位数，逐次交替编码顺序；第二轮反转规模及编码顺序。串行运行，不同时测试、构建或做其他性能测量。每次在计时外解析 Blob，逐条验证所有夹具字段、ID/顺序、备份头及私有字段未泄漏。

| 文件字节数，两轮一致 | 旧缩进 JSON | 紧凑 JSON | 减少 |
| --- | --- | --- | --- |
| 100 条 | 157,952 | 151,332 | 6,620（4.2%） |
| 10,000 条 | 15,884,552 | 15,224,532 | 660,020（4.2%） |

正式生产调用形式的耗时如下，单位 ms：

| 场景 | 第一轮：旧 → 新 | 第二轮：旧 → 新 |
| --- | --- | --- |
| 100 条，消息往返至 Blob 完成 | 1.1 → 1.0 | 8.6 → 8.3 |
| 10,000 条，消息往返至 Blob 完成 | 61.2 → 55.9 | 61.7 → 55.9 |
| 10,000 条，仅 JSON 生成 | 8.3 → 3.1 | 8.0 → 3.1 |

正式两轮的大数据总耗时减少约 5–6ms，JSON 生成部分减少约 5ms。早期原型采用 `JSON.stringify(data, null, undefined)`，仍保留 `null` 参数，其大数据总耗时仅减少 0.6–1.2ms；不与正式单参数结果混合统计。所有样本均保留。

[V8 官方说明](https://v8.dev/blog/json-stringify)指出，普通数据的紧凑序列化可使用快速路径；[当前引擎实现](https://raw.githubusercontent.com/v8/v8/main/src/json/json-stringifier.cc)的入口要求 replacer、space 均为 undefined。单参数调用符合该条件，实测的 JSON 生成收益与之相符。这是依据文档和结果的解释，没有直接跟踪本机浏览器的引擎分支，也不将 Chrome 收益外推到其他引擎。

计时包含缓存命中的后台读取、消息序列化/传输和接收、页面 JSON 生成与 Blob 创建，不包含下载写盘、表格渲染、后台休眠唤醒、完整工具栏交互或导入准备。100 条在第二轮明显更慢，两种编码相近；保留差异，不据此宣称稳定小数据速度提升。

## 分配与未采用的候选

正式计时结束后再采样分配，采样间隔 32KiB，包含后续被 GC 的对象；后台和接收页分别取样。以下是一次操作的 V8 采样分配量，十进制 MB：

| 10,000 条 | 第一轮：旧 → 新 | 第二轮：旧 → 新 |
| --- | --- | --- |
| 接收页 | 47.19 → 45.77 | 46.76 → 45.92 |
| 后台 | 15.76 → 16.12 | 15.91 → 16.15 |
| 两者采样量之和 | 62.94 → 61.88 | 62.67 → 62.07 |

总差异约 0.60–1.06MB，后台单独存在小幅波动；采样不能当作精确分配、峰值堆、Blob 外部缓冲或进程 RSS，也不能证明长期无泄漏。

另在临时副本中测试过“后台直接生成缩进备份 JSON，消息返回字符串”。两轮 10,000 条的总耗时为 60.8 → 63.4ms、66.5 → 68.9ms，均稍慢。第二轮接收页采样减少约 14.22MB，但后台增加约 16.82MB，合计约 62.25 → 64.84MB。仅看接收页会误判收益，因此没有采用这个新消息接口。该原型的计时、采样和正式样本分开保存。

## 验收与复跑

- 27 个测试文件、216 个测试通过，类型检查及 Chrome/Edge/Firefox 构建通过。
- 实际 Chrome 页面下载紧凑备份，核对全部 10,000 条及富文本；分别上传旧缩进、新紧凑文件，经覆盖确认恢复，全部记录与下载数据一致。三项大数据界面验收通过。
- 既有 17 项备份、搜索、分页、排序、同步和错误路径界面验收通过，页面无异常。
- 脚本语法与浏览器启动失败时清理临时用户目录的检查通过。

```sh
PLAYWRIGHT_MODULE='/path/to/playwright/index.mjs' CHROME_PATH='/path/to/Chrome for Testing' node scripts/backup-performance.mjs
PLAYWRIGHT_MODULE='/path/to/playwright/index.mjs' CHROME_PATH='/path/to/Chrome for Testing' node scripts/backup-performance.mjs --reverse
```

`EXTENSION_PATH` 可指定构建后的扩展。脚本测量两种编码，并在测量后执行 10,000 条实际下载与两种格式恢复验收。使用临时用户目录与合成数据，结束或启动失败时清理浏览器用户目录；下载与结果保留在打印的独立产物目录。

原始逐次时间、分配样本尺寸直方图、产物路径、源码哈希及检查范围：[performance-backup-results.json](./performance-backup-results.json)。省略没有调用栈树对应的采样 node ID，保留样本尺寸计数及总字节数，原始完整数组仍在本机产物文件中。
