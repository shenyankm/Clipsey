# 冷深页的一次主键扫描实验（未采用）

2026-10-12；生产基线 `97384e5`，承接[深页复访的有界主键缓存验收](./performance-page-keys.md)。以 10,000 条为主、100 条为辅，额外验证 10,001 条门槛与 20,000 条窗口外回退。全部样本、源码哈希与初始原型快照见[完整数据](./performance-one-pass-results.json)。

## 结论

不接入生产。Chrome 155 的 10,000 条冷深页明显受益：创建时间约 42–44ms → 24–25ms，正文约 107–112ms → 58–62ms。但 Firefox 同规模创建时间反而约 1–2ms → 3ms；Chrome 超过窗口后也回退，20,000 条正文升序约 220–221ms → 280–282ms。只在主要规模变快不足以支持加入这条路径。

应用源码保持 `97384e5` 的内容。这次只保留实验夹具、两个现有运行器的新参数和报告，没有依赖、权限、公开 API、schema 或应用缓存改动。首次冷计数与未访问深页仍是待优化问题。

## 实验方法与门槛成本

同一 clips/metadata 只读事务先并行读版本标记与 `getAllKeys(query, 10001)`。最多读到 10,000 个命中时，数组长度就是精确 total，再按原生顺序取本页主键并读取正文。超过该窗口时仍需原生 count；若数组覆盖目标页则直接取主键，否则再走原有游标。降序按精确 total 换算升序位置，再反转本页；不要求新版 direction 选项。原生 getAllKeys 返回命中记录的主键，count 参数限制返回量，方法依据见 [IndexedDB 标准](https://www.w3.org/TR/IndexedDB/#dom-idbindex-getallkeys)。

10,001 个返回值不能证明整个结果只有 10,001 条，因此必须计数。Chrome 的 10,001 条无范围场景已出现小幅回退；20,000 条升序深页偏移 18,000 不在前缀窗口，又增加原游标定位成本。降序该页映射到前缀约 2,000 的位置，能够省掉游标，但仍需额外 count，方向收益不一致。

范围按命中数判断，不按库大小：10,001 条库的复合时间范围约 6,005 个命中，仍走完整主键数组；20,000 条库的范围超过窗口，升序也回退。这一边界不因提高固定窗口而消失，只会移到另一个规模。

原型每次最多返回 10,001 个临时主键，没有跨查询缓存。五字符 ID 的字段权重约 420,128 字节（10,000 个主键）；窗口上限约 420,170 字节。按每键 32 字节加 UTF-16 长度、数组固定 128 字节估算，不是实际堆、峰值或 RSS；真实长主键仍可占更多空间。当前生产复访缓存最多只保存 1,600 个主键，不能将两者的内存代价混为一谈。

## 100 条小数据与测量边界

Chrome 正序冷末页为当前 0.5–1.4ms、原型 0.4–0.8ms；Firefox 两轮为 0–1ms。Chrome 反序先经历更大的库再 clear 重写 100 条，范围为 0.4–13.8 → 0.3–3.9ms，其中正文降序为 11.9 → 3.9ms。保留这些高延迟样本，不据此声称一般小数据提速。

每个方法在每次样本前关闭并重开数据库连接，打开连接不计时，不提前 count。方法交替执行，每次核对字段后停止计时；参考全量读取、合成写入和准备均在计时外。只测冷深页，没有把生产已缓存的复访结果与每次扫描的原型混在一起，也没有测试点击到绘制耗时。

正式夹具冻结后，串行运行 Chrome 正序、Chrome 反序、Firefox 正序、Firefox 反序，无测试、构建或 CPU/分配采样重叠。共 160 场景、2,240 个计时查询。另在每个规模检查新增记录、溢出计数、缺失索引字段、数值旧主键、缺版本标记、前缀外原游标和越界空页。初始两版 Chrome 探索样本与源码快照单列，不用于正式结论。

环境沿用前阶段：macOS / Node 22.23.2，安装版 Chrome 155.0.8059.39（Headless UA 155.0.0.0），带 Playwright 补丁的 Firefox Nightly 153.0 / geckodriver 0.37.1；正文约 640 字符、HTML 约 840 字符，含中文、缺标题和重复索引值。独立临时配置与合成来源，不访问用户摘录。
