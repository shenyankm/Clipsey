# 高亮恢复调度与响应性验收

后续[消息任务兼容路径](./performance-message-yield.md)进一步减少缺少 `postTask` 时的批量偏移恢复等待，并保留响应性和完整扫描的不利结果；以下为原阶段测量。

2026-10-12；基线 `c778512`。延续[文本遍历游标验收](./performance-text-cursor.md)。主要库规模仍为 10,000 条摘录；本轮另测 100/10,000 段页面，以及每批 20、100、1,000 条高亮，分别记录这些数量。

## 改动与选择

原实现每条新高亮固定等待 8ms，小页面恢复 100 条约需一秒。现在默认等待为 0，仍在每项之后让出主线程；有 `scheduler.postTask` 时提交一个普通后台任务，缺少该 API 时使用 `setTimeout(0)`。显式 `setThrottle(ms)` 的正数等待继续保留，没有增加依赖、设置或永久缓存。

后台任务携带本批次的取消信号。取消正在等待的任务后，恢复返回 `false` 并断开 DOM 观察器；非取消异常继续向上传递。各项仍重新检查取消、外部修改和目标可见性，定位顺序及绘制规则不变。

未采用 `scheduler.yield()`：它提高续跑优先级，设计说明见 [Chrome 官方文档](https://developer.chrome.com/blog/use-scheduler-yield?hl=en)。实际候选的普通取消定时器直到 1,000 条全部绘制才运行，延迟约 1,088ms；返回 `true`，未通过取消验收。普通优先级 `postTask` 虽可取消，但全文回退的最大动画帧间隔中位数约 33ms；最终后台任务版本约 17ms，因此选用后者。

## Chrome 对照

Headless Chrome 155、macOS、生产源代码与真实 DOM，只有设置消息使用空响应。每次新建独立浏览器配置。每项预热一次，七次取中位数；两轮反转场景和绘制顺序。正式源码对照的执行顺序为基线正序、最终正序、最终反序、基线反序，中间包含候选实验与功能检查；最后一轮交叉基线在最终实现的定时器回退及原生验收之后运行。所有计时串行，期间没有测试、构建或分配采样。

夹具构造后等待两个动画帧，再开始恢复计时，排除初次布局；计时包含引擎原有的 DOM 就绪/空闲等待。每次核对全部目标、绘制数量、完整原文及清除后的原文。下表为完整恢复耗时中位数，单位 ms：

| 页面段落 / 批次高亮 | 第一轮：基线 → 当前 | 第二轮：基线 → 当前 |
| --- | --- | --- |
| 100 / 20，带偏移 | 188.7 → 0.8 | 193.1 → 3.7 |
| 100 / 100，带偏移 | 964.1 → 4.3 | 949.9 → 4.0 |
| 10,000 / 20，带偏移 | 213.4 → 23.5 | 226.3 → 17.3 |
| 10,000 / 20，全文回退 | 462.9 → 364.1 | 498.0 → 361.7 |
| 10,000 / 100，带偏移 | 1,050.3 → 28.0 | 1,050.6 → 28.6 |
| 10,000 / 1,000，带偏移 | 10,583.5 → 193.7 | 10,497.9 → 267.5 |

10,000 段带偏移恢复 1,000 条减少约 97.5–98.2%；恢复 20 条减少约 89–92%。全文回退减少约 21–27%，仍受同步全文扫描影响。100 段恢复也明显减少固定等待；接近毫秒的数值受计时与空闲回调波动影响，不作为硬性能阈值。

## 响应性与取消

计时内用 16ms 普通定时器和连续 `requestAnimationFrame` 采样，记录每次恢复中最大的间隔及长任务条目。这是合成页面探测，不是 INP、真实用户输入延迟或帧率测量。

- 10,000 段 / 1,000 条：基线最大定时器间隔中位数 24.4/24.8ms，当前 19.9/23.5ms；两版本最大动画帧间隔中位数均约 16.7–16.8ms。
- 20 条全文回退：定时器间隔约 26–29ms，动画帧间隔约 16.8ms。最终候选各个正式样本未记录到长任务，不据此推断所有页面没有长任务。
- 独立取消夹具在首项绘制后用普通定时器发起取消。最终两轮都在绘制 1 条后返回 `false`，取消后没有继续绘制；延迟在计时粒度以内，不能解释为零成本。

最初没有等待夹具布局完成，测到了 100ms 以上的首帧间隔；正式计时采用一致的两帧准备步骤。旧夹具结果作为实验记录单独保留，不能与正式数据合并。初次页面布局与真实繁忙页面的体验仍须另外评估。后台任务可能被页面更高优先级工作推迟；取消信号避免等待中的任务持续保留观察器。

## 不支持调度 API 时

在同一 Chrome 中强制移除夹具的 `scheduler`，用最终源码重复正反两轮，确认回退实际使用定时器：

| 场景 | 第一轮：基线 → 定时器回退 | 第二轮：基线 → 定时器回退 |
| --- | --- | --- |
| 100 段 / 20 条，带偏移 | 188.7 → 71.4ms | 193.1 → 75.1ms |
| 10,000 段 / 20 条，带偏移 | 213.4 → 97.2ms | 226.3 → 94.3ms |
| 10,000 段 / 1,000 条，带偏移 | 10,583.5 → 5,621.9ms | 10,497.9 → 5,830.5ms |

1,000 条恢复减少约 44–47%，仍有逐项定时器开销。两轮取消均发生在第 2 条后，未继续绘制。全文回退的最大定时器间隔中位数约 39/47ms，动画帧间隔约 17/33ms；不能把后台任务的响应性结果套用到回退路径，也不把 Chrome 强制回退当成 Firefox 性能验收。

## 检查与原生扩展

241 个测试、28 个文件通过 coverage（语句 59.43%、分支 55.01%、函数 61.35%、行 59.91%）。类型检查、Chrome/Edge/Firefox 构建、脚本语法和 diff 检查通过；三个 content 构建产物确认默认等待为 0、后台任务与取消信号均保留。构建仍有超过 500kB 的共享 UI 代码块警告，Firefox 仍提示发布配置。

Chrome for Testing 153.0.8010.12、带 Playwright 补丁的 Firefox 153.0 Nightly（build ID `20260722112722`，geckodriver 0.37.1）各通过 17 项实际扩展验收：

- 真实 10,000 条库供应 20 条页面记录，实际消息恢复、倒序、重复、全文回退及清除通过。
- 新增 1,000 段页面与 1,000 条合成恢复载荷，经扩展消息倒序绘制、重复、清除，所有目标与原文正确；这批载荷没有写入摘录库。
- 两浏览器的页面定时器均在第 1 条绘制后执行，早于批次结束；不是只验证微任务回调。
- 原生选区、相邻文字、外部插入、CSSOM/媒体条件变化、隐藏重复文字/选择器及可见性覆盖继续通过。

依据新批次的较短耗时，为外部自动化调整视口留出窗口，媒体夹具的中间项由旧 20/50 条扩为 Chrome 2,000 条、Firefox 5,000 条；仍断言目标绘制时前缀已经隐藏且保留原始重复文字目标。该夹具不作为耗时基准。

隐藏目标的选区验收额外保存一条记录，最终库数量 10,001 已断言。Chrome 页面/扩展异常为空，Firefox 扩展 URL 来源的非警告错误为空；使用独立临时配置并在退出后清理。原始数据、实验候选、源码 SHA-256 和原生结果见 [performance-highlight-scheduling-results.json](./performance-highlight-scheduling-results.json)。
