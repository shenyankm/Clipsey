# 按网址读取的生产候选与验收

日期：2026-10-11；基线：`38702cddd97d3b2e15baaf65f881af04d0258e22`。按用户确认，以 10,000 条为主要规模，兼顾 100 条。本地分支 `sheny/performance-indexed-url-cache`；尚未推送或合并，整个性能优化目标仍在进行。

候选把稀疏网址读取接入生产路径。读取收益已复现，但批量写入明显变慢，不能作为全面性能优化已经完成的结论。延续[原型实验](./performance-url-read.md)；逐次样本和验收结果见[原始数据](./performance-indexed-url-cache-results.json)。

## 数据和缓存边界

数据库从 v3 升至 v4，新建独立 `clipUrls` 存储，索引键为规范化基础 URL、原始创建时间和 ID。摘录正文保留原有八个索引，不增加私有字段；普通读取及备份格式保持兼容。

升级在版本事务内逐条回填，不改写原记录，不删除未知存储。异常 ID/日期或主键不一致的旧记录写入回退标记，继续使用既有全量读取规则，防止只标准化子集改变跨页面去重结果。旧的 out-of-line 主键也沿用全量读取。空值和额外旧字段保留在数据库中，没有新增对所有异常记录都可在界面显示的保证。

所有已找到的添加、覆盖、删除、清空、批量导入与旧存储迁移入口，都在同一事务内维护正文和网址索引。正文或索引写入失败，两者一起回滚；没有依赖定期修复缺失索引。直接从外部修改原生 IndexedDB、绕过这些入口，不在一致性保证内。

页缓存只保留一个基础 URL，最多 2,500 条；查询参数变化仍按精确匹配优先、高亮去重及原有时间/ID 顺序返回。全量缓存已存在或正在加载时沿用全量快照；页缓存不会被当作全库数据。写入/同步使两类缓存失效，旧请求重试，失败向上传播，输入和返回对象彼此隔离。

超过上限时回退全量读取。命中至少 64 条时，再探测最多 257 个元数据主键；若全库不超过 256 条且命中至少一半，也使用批量读取，避免小库的大量单条请求。探测不读取无关正文，也不执行全库计数。上限是本机合成数据的取舍，更长正文或不同硬件需要重新测量。

## 原生读取对照

macOS、Node.js 22.23.2、Headless Chrome 155.0.0.0、真实 IndexedDB，独立临时目录。正文约 640 字符并带 HTML，日期完整；匹配项使用两个查询参数变体，其余为不同来源。每项预热后七次取中位数，两轮交换规模及命中数顺序。计时内执行真实存储调用；扩展消息传输替换为桩，结果顺序、精确查询优先和全量数量在计时外断言。没有同时测试、构建或运行其它性能脚本。

冷指清空应用缓存，数据库已经准备好，不是磁盘冷启动或休眠后台启动。夹具切换后的后台存储工作和 GC 仍会影响样本；不以毫秒阈值做 CI 断言。

| 无命中 | 66.1 / 67.7 | 0.1 / 0.1 |
| 命中 10 条 | 159.3 / 72.5 | 0.5 / 0.6 |
| 命中 100 条 | 93.6 / 68.5 | 2.7 / 2.4 |

稀疏和中等命中明确减少读取无关正文的成本。密集回退保留全量缓存，但第一轮全部命中增加 19.2ms，第二轮减少 3.1ms，不能声称密集读取也稳定加快。命中 10 条的热读取约由 0.002ms 变为 0.003–0.004ms；不把这类微小差异解释为界面体验变化。

100 条命中 1 条：0.6–2.7ms → 0.2ms；命中 10 条：0.7–2.8ms → 0.2–0.3ms。全部命中为 0.5 / 3.3ms → 1.0 / 8.0ms，波动明显且存在额外探测开销；不能宣称小数据全部场景都加快。全量缓存专项中，100 条完整日期冷全量读取为 0.7 / 0.6ms → 0.6 / 0.6ms；10,000 条为 65.1 / 68.1ms → 78.2 / 66.1ms，没有稳定的全量读取改善证据。

候选校准时，每次统计两张表总数使稀疏读取约需 21–30ms，已移除。完整索引维护由升级及写入事务保证。按主键回读 5,000 条约需 97.4ms，未采用；2,500 条约需 46–55ms，因而采用有界页缓存。原始校准结果单独保留，没有充作最终候选的复测结果。

另各运行一轮 V8 分配采样，每项七次取中位数，采样间隔 16,384 bytes，准备和结果校验在采样之外。10,000 条命中 1 条由约 21.94MB 降至 0.016MB，命中 100 条由约 21.45MB 降至 0.283MB；全部命中约 20.62MB → 21.24MB。小分配接近采样粒度，不推算精确百分比或零分配。这不是峰值存活堆、底层缓冲、RSS、数据库磁盘占用或长期无泄漏证明。

## 写入及升级代价

同一写入夹具，两轮顺序为基线、候选、候选、基线，操作预热后七次取中位数。整库替换使用实际 `saveClips`，清空和单条写入亦使用生产服务。

| 10,000 条，ms | 基线：第一轮 / 第二轮 | 候选：第一轮 / 第二轮 |
| --- | --- | --- |
| 添加一条 | 0.3 / 0.3 | 0.4 / 0.4 |
| 替换同高亮 | 0.3 / 0.4 | 0.5 / 0.4 |
| 删除一条 | 0.2 / 0.2 | 0.3 / 0.3 |
| 整库替换 | 1,699.6 / 1,602.2 | 2,538.9 / 2,627.7 |
| 清空 | 572.7 / 489.7 | 680.9 / 608.6 |

100 条整库替换为 10.0 / 8.3ms → 18.0 / 13.6ms。索引维护有实际成本，尤其大量恢复/导入；该退化尚未解决。后续应比较降低索引维护成本的方案，不能只引用稀疏读取结果直接发布。

最终两轮真实 v3→v4 回填 10,000 条约为 751.6 / 754.1ms。逐字段比较原记录，并验证未知存储和数据保留。这是一次升级耗时，每轮只测一次；不代表普遍上限。额外数据库空间未测量。成功升级后，旧版本不能直接用 v3 打开 v4 数据库；失败回滚测试不代表已经支持自动降级。旧库中若未知存储已占用 `clipUrls` 名称，升级安全中止，保留原库。
